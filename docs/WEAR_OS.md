# Wear OS companion

## Pairing and first run

Build with JDK 17 and Android SDK platform 37. The `:wear` module supports Wear OS API 30 and later. Install the phone app on the paired Android phone and the Wear app on the watch. Both release variants must have the same application ID and signing key. Set a school and home class on the phone; open the watch app after the phone has cached a timetable. The watch has no school login or direct EduPage connection. Use **Sync now** to ask the connected phone to republish its cached days.

The watch shows today's lessons, a 14-day day selector, lesson details, the last sync time and an explicit missing-day state. It follows the phone's language, color palette, theme choice, saved class, time zone, reminder toggle and lead time. Change these settings on the phone. The cache is written atomically and survives watch restarts or disconnection. The last-synced time remains visible while offline. An empty synced day is distinct from an unsynced day.

The phone publishes a versioned, bounded snapshot through Wear Data Layer. It contains display-ready lesson labels and times for the saved home class, never credentials, raw EduPage responses, unrelated classes or device identifiers. The watch rejects unsupported/corrupt/oversized snapshots and older publications. Phone settings changes enqueue a new publication. Reconnect and open either app to trigger a refresh if the background delivery was delayed. A watch `Sync now` request cannot download fresh school data when the phone itself is offline; the phone first needs a current timetable.

Class reminders on the watch use at most two days of cached data, inexact alarms and the synced toggle/lead time. While connected to the phone, the watch relies on the phone's bridged reminder; when disconnected it can show its own reminder if notification permission is granted. Watch alarms are rebuilt after reboot and clock changes. An inexact alarm can arrive late and is suppressed outside its valid window. This is a best-effort companion to the phone's reminders; verify notification bridging and permission on each watch model. The short/long text watch-face complication shows the current or next class from the local cache, or an empty/sync prompt. It refreshes on snapshot change and requests a periodic update at 30 minutes; the watch face controls actual scheduling.

## Validation

CI runs JVM tests for snapshot compatibility, bounds, selection and older-packet handling; lint and debug/release assemblies of every module; the existing phone emulator suite; and static analysis. A paired watch emulator or physical watch is needed for Data Layer transport, complication selection, notification bridging, runtime permission, locale/layout and round-screen testing. Validate disconnected phone, disconnected watch, overnight rollover, school change, empty versus missing day, timezone/DST change, reboot, revoked notification permission and stale alarms before release. Do not publish a Wear release solely on successful compilation.

## Battery protocol

Run a controlled **physical watch** power trial because phone `PowerMetric` and emulator battery estimates do not measure watch drain reliably. Use the same watch, OS/build, face/complication, brightness, radios, wrist settings and school snapshot in each trial. Charge to the same starting level and let the watch settle; record the 24-hour percentage drop and Android battery usage for three baseline trials without EduSchedule, then three with the companion installed, paired and a representative school day (including reminders). Repeat a disconnected trial and a no-complication trial. Record watch model, battery capacity, firmware, baseline/app mean and range, notification count, refresh count and measured duration. A meaningful regression warrants tracing Data Layer transfers, wakeups and alarms with Android Studio Energy Profiler and `adb shell dumpsys batterystats`; reset stats before each comparable run. Battery percentage is coarse: report ranges, not false milliwatt-hour precision. Investigate any repeatable extra drain above 2 percentage points per 24 hours, unexpected wakeups or a sync loop before release; this threshold is a review trigger, not a claim of passing measurement.

Implementation keeps data writes change-driven with a daily heartbeat, caps the payload and days, coalesces WorkManager jobs, uses bounded inexact alarms and avoids network work in the complication. CI can guard those invariants, but cannot replace physical battery measurement. Add the actual measured results to release notes after device trials; none have been collected by this change.
